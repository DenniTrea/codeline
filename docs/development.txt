MICROSOFT REGISTRATION — REQUIRED BEFORE LIVE SIGN-IN
1. In the university Microsoft Entra directory, open App registrations and choose
   New registration. Name: CodeLine. Supported accounts: this directory only.
2. Add Web redirect URI: http://localhost:5173/auth/callback (not SPA).
3. Copy directory/tenant ID and application/client ID into backend/.env.
4. Create a client secret if university policy permits it, and put its VALUE
   directly into backend/.env as MICROSOFT_CLIENT_SECRET. Never send it in chat.
5. Leave implicit access/ID token grants off. The app uses MSAL Node, code flow,
   PKCE, state and nonce, with minimal openid/profile/email scopes. No Graph
   directory/mail permissions are needed. Tenant consent policy may require IT.
6. Restart npm run dev, then sign in using the real university account.
The backend registers new validated identities as students only, using oid for
users.id. It never generates an identity or allows a role picker. Student profile
names come from the verified identity. Existing users retain their database role.
Single-tenant login can include tenant guests: a stricter members-only policy
needs university-approved membership information before implementing exclusions.

ROLE PROVISIONING
An authorized database administrator must approve staff access separately. After
real sign-in, inspect the exact user and set only the approved user's role to
lecturer/admin via DataGrip or a reviewed parameterized admin command. The app
never promotes the first user automatically. No role was changed during setup.
Students see enrolled courses only; TA/lecturer/admin see the course catalog.
Only lecturer/admin can create courses. The current schema has no staff-course
ownership relation, so staff access is global; per-course staff authorization
needs a product/schema decision rather than an invented owner column.

SESSIONS AND DEPLOYMENT
Sessions live in an encrypted local file store under backend/.local/sessions,
with an eight-hour lifetime and a stable SESSION_SECRET. That folder is private
and ignored; it contains identity/flow state, never database credentials or the
MSAL token result. Keep it on persistent VM storage if deploying.
For production set NODE_ENV=production, a strong stable SESSION_SECRET,
FRONTEND_ORIGIN=https://your-host, MICROSOFT_REDIRECT_URI=https://your-host/auth/callback,
and DATABASE_URL pointing to the local VM PostgreSQL server. Register that exact
HTTPS Web callback in Entra. Nginx must proxy the same paths and set trusted
X-Forwarded-Proto; Express trusts one local proxy and uses Secure cookies in
production. Only the local Nginx proxy should reach Express. No production Nginx,
TLS or application service deployment was performed in this work.
Socket.IO is installed and rejects gameplay connections until full room/enrollment
permission checks exist. Exercise editor and game logic are not implemented yet.
Course roster management is available in the admin panel described below.

Overview: totals for accounts, student-role users, courses, enrollments and open
rooms; database readiness. Accounts: search/pagination, role changes and student
profile updates. Courses & enrollment: create/edit course, manually planned count,
actual enrolled count, student search/pagination, bulk add (up to 50) and remove.
Users must sign in with university Microsoft once before an admin can enroll them;
the panel cannot manufacture Microsoft IDs or local-password accounts.

All /api/admin routes require a current database admin role. Mutations require the
expected Origin. Role changes are serialized and recheck the acting admin inside
the transaction; own-admin demotion is rejected. New student roles get a profile,
and existing profiles and game history are retained when roles change. Enrollment
inserts are idempotent, require registered student-role accounts, and never alter
courses.studentCount. Removing enrollment or changing an active participant away
from student is rejected until their open sessions end. Existing session rosters
are not rewritten. Hard deletion of accounts and account suspension are not
included; the current schema has no suspended flag. No migrations were added.
Admins can delete a course from Courses & enrollment after typing its exact code.
Deletion removes its enrollments and retains student accounts. Courses with any
exercise (including a soft-deleted exercise) are protected, preserving game history.
The backend rechecks admin access, code and enrollment count inside a transaction,
locks the course, and rejects stale confirmation details before deleting anything.
Successful admin mutations emit actor/action/target IDs to server logs, excluding
passwords, tokens and student profile content. This is an operational log, not a
durable database audit trail.

LOCAL ROLE TESTING — 24 November 2026
The development-only banner lets the signed-in admin test student or lecturer
permissions, then Return to admin. The saved users.role and validated Microsoft
identity never change. The override lives in that browser session; normal tabs
share a session, so use separate browser profiles for simultaneous roles.
The backend applies the effective role to course and admin authorization, not just
the UI. It rechecks the saved admin role on every request; a demoted account cannot
keep using the testing controls. No anonymous login or invented identity exists.

Opt in locally with DEV_ROLE_TESTING=true in backend/.env and npm run dev.
The dev script sets NODE_ENV=development. Testing also requires a loopback frontend
origin, request hostname and socket peer. In production or without the explicit
flag the routes return 404 and session overrides are ignored. Keep the flag false
in deployment. No migration is needed.

To test student visibility, create a course as lecturer/admin, expand Test my
student enrollment, choose a course and click Enroll my account. This explicitly
saves the real admin's own student profile if absent and a real courseStudents
row. Remove my enrollment reverses that membership, subject to the same open-game
guard. Other student accounts are never enrolled by these development endpoints.
The banner is not a sandbox: course creation and enrollment changes persist in
the connected database. Switching roles alone only changes the session.
